# Примеры консольных ответов

## Назначение

Пример ответа показывает уже определённую внешнюю модель и её сериализацию, но
не является владельцем требования. Если для примера требуется отсутствующее
правило, сначала согласовать и добавить его в нормативный раздел результата.

## Обязательный состав

Для каждой конечной команды приводить успешный ответ в каждом поддерживаемом
формате, если формы представления различаются. Если команда не выводит успешный
результат, явно показать отсутствие вывода вместо вымышленной модели.

Общий документ ошибочного результата содержит по одному примеру каждого
поддерживаемого формата, форма которого отличается. Конечная команда повторяет
эти примеры только при собственной модели ошибки или явном отклонении от общего
контракта.

Для режимов подробности не повторять стабильный результат, если его состав не
меняется. Отдельный пример logging-записи добавлять в observability-документ,
когда это требуется для понимания logging-контракта.

## Соответствие нормативной модели

Проверять каждый пример ответа по таблице полей:

- каждое показанное поле определено в модели;
- обязательные поля присутствуют, условные — соответствуют условию;
- лишних полей нет;
- внешнее имя, регистр и представление значения совпадают;
- соблюдены ограничения, допустимые значения, `null` и правила отсутствия;
- поля расположены в согласованном порядке;
- сквозной идентификатор занимает закреплённую позицию;
- успешный или ошибочный ответ соответствует заявленному статусу процесса.

Разные форматы одного результата используют одинаковые смысловые значения. Если
контракт требует одинаковый набор и порядок полей, примеры должны совпадать по
обоим признакам; различается только сериализация.

## Текстовый формат

Показывать ответ в блоке `text` ровно в наблюдаемом виде. Сохранять согласованные
имена полей, разделители, пробелы, регистр, порядок строк и завершающий перевод
строки, если он является частью контракта. Не добавлять пояснения внутрь блока.

Если результат является одним сообщением, показывать только это сообщение. Если
формат использует пары «имя — значение», каждая строка и каждое значение должны
соответствовать таблице модели.

## JSON

JSON должен быть синтаксически корректным. Форматировать его многострочно:
открывающая и закрывающая скобки — отдельно, каждое поле — на своей строке,
вложенность — с единым отступом. Использовать JSON-типы, а не строковые имитации
чисел, boolean или `null`.

Не добавлять до или после JSON человекочитаемый текст в тот же поток, если
контракт обещает один машиночитаемый объект.

## Ошибочные ответы

Пример ошибки содержит только безопасные внешние поля. Не включать внутреннее
исключение, stack trace, имя класса, путь к файлу, параметры подключения или
другие детали реализации.

Человекочитаемые сообщения используют согласованный язык. Машинные имена полей,
коды и значения перечислений следуют внешнему контракту и не переводятся из-за
языка окружающей документации.

Если ошибка возникает до получения корреляции или другого условного контекста,
пример не должен искусственно добавлять такое поле.

## Безопасные значения

Использовать очевидно вымышленные данные. Не включать рабочие идентификаторы,
персональные данные, токены, пароли, строки подключения и секреты. UUID, даты,
URI и другие структурированные значения должны быть синтаксически корректными,
если это проверяется контрактом.

Не добавлять пример для каждого значения enum или каждой однотипной ошибки.
Новый пример оправдан отдельной формой ответа либо реальной неоднозначностью,
которую нельзя устранить одной нормативной таблицей.
