# Контракт CLI

## Общие решения

До детализации команд согласовать:

|Решение|Что определить|
|:---|:---|
|Исполняемая команда|Имя, область использования и потребители|
|Иерархия|Группы, действия и допустимая глубина|
|Справка|Полная и короткая формы, содержимое каждого уровня|
|Неполный вызов|Ошибка, краткая подсказка или полная справка; поток и статус|
|Форматы|Допустимые значения, default и назначение каждого формата|
|Подробность|Режимы, default, взаимное сочетание и влияние на результат и логи|
|Потоки|Размещение результата, справки и logging-записей|
|Статусы|Закрытый набор статусов завершения и условие каждого|
|Корреляция|Получение, создание, валидация, передача и возврат|
|Служебные команды|Наличие help, version и других общих возможностей|

В качестве стартового варианта можно предложить `--format` / `-f`, форматы
`text` и `json`, `text` по умолчанию; `--quiet` / `-q`, результат без опции,
`--verbose` / `-v`, `--trace`; `--help` / `-h`; статусы `0` и `1`; стабильный
результат в `stdout`, logging-записи в `stderr`. Каждый вариант становится
требованием только после согласования. Не добавлять `--version` автоматически.

## Паспорт конечной команды

Единой таблицей фиксировать исполняемую команду, путь подкоманд, область
использования, доверие или идентичность, форму входа, форму результата,
application-операцию и статусы завершения. Не пересказывать после паспорта его
поля общей прозой.

## Синтаксис, аргументы и опции

Показать полный синтаксис с обязательными и условными частями. Позиционные
аргументы и именованные опции описывать отдельно, если используются оба вида.

Для каждого значения фиксировать:

|Внешнее имя|Представление|Обязательность|Default|Правила|Смысл|
|:---|:---|:---|:---|:---|:---|

Указывать полную и короткую формы, отсутствие значения, пустое значение,
повторение одиночной опции, дубликаты коллекции, разделитель, порядок,
нормализацию и неизвестные опции, когда они применимы. Для условно обязательных
значений явно описывать допустимые сочетания.

## Справка и неполный вызов

Для корневого, группового и конечного уровней определить:

- синтаксис явного вызова справки и равнозначность форм;
- точный состав справки текущего уровня;
- формат, поток и статус завершения;
- влияние остальных общих опций;
- вызывает ли справка application-операцию и создаёт ли logging-записи.

Отдельно определить вызов каждого неконечного уровня без обязательной
подкоманды. Не считать автоматическую справку единственно возможным поведением.
Если это ошибка, привести безопасное сообщение и подсказку явного вызова help.

## Внешняя валидация

Описывать только правила CLI-границы: наличие, синтаксическое представление,
допустимые внешние значения, сочетания опций и неизвестный ввод. Не выдавать
бизнес-правило за транспортную валидацию.

Для отклонения фиксировать, вызывается ли application-операция, какой результат
видит пользователь и какой статус получает процесс.

## Преобразование в application-вход

CLI-модель и application DTO являются разными контрактами. Показывать mapping:

|Внешнее значение|Сведение application-входа|Преобразование|
|:---|:---|:---|

Включать аргументы, опции, идентичность, доверенный контекст и корреляцию. Явно
отмечать внешние значения, которые не передаются, и application-поля, которые
CLI не заполняет. После успешной внешней валидации конечная команда по умолчанию
вызывает выбранную application-операцию один раз; другое поведение согласовать.

## Успешный результат

Внешнюю модель описывать поле за полем:

|Сведение|Внешнее имя|Представление|Обязательность|Правила|
|:---|:---|:---|:---|:---|

Фиксировать источник каждого поля в публичном application-результате,
преобразование, `null`, отсутствие, порядок и правила сериализации. Не выдавать
application DTO наружу напрямую.

Для нескольких форматов явно определить, представляют ли они один семантический
результат. Стартовый вариант — одинаковые поля и порядок для `text` и `json`;
отклонение должно быть согласовано и описано. Язык внешних имён полей и
человекочитаемых значений согласовывать отдельно.

Каждый результат сопровождать примерами по
[response-examples.md](response-examples.md).

## Ошибочный результат

Различать:

- ошибку внешнего CLI-ввода;
- публичный ошибочный application-исход;
- неизвестный внутренний сбой на CLI-границе.

CLI преобразует только публичные application-исходы. Не описывать domain и не
делать domain-ошибку непосредственным источником консольного результата.
Стабильный ошибочный результат не содержит внутреннее исключение или stack
trace.

Для общей внешней ошибки определить поля, обязательность, порядок, язык
машинных имён и допустимый язык человекочитаемых сообщений. Не вводить
прикладные коды ошибок, если пользователь их не требует. Каждому классу исхода
назначить один из согласованных статусов завершения.

## Результат, подробность и logging

Стабильный результат не должен менять состав из-за включения подробности, если
иное не согласовано. Зафиксировать влияние каждого режима на успешный и
ошибочный вызов, а также quiet-поведение при сохранении статуса завершения.

Если результат и logging разделены, опция формата результата не должна неявно
менять logging renderer. Logging-профиль, поля, события, уровни и stack trace
принадлежат observability-документации. Короткоживущему CLI не назначать worker-
события lifecycle, readiness, heartbeat, цикла или остановки без реального
процессного поведения.

Не выводить и не логировать секреты, полный набор аргументов, необработанный ввод
или чувствительные предметные значения без явного разрешения.

## Корреляция, повтор и совместимость

Для корреляции определить внешний источник, fallback или отсутствие, формат,
момент доступности, передачу application и присутствие в результате и логах.
Положение сквозного идентификатора в результате согласовывать явно.

Описать смысл повторного запуска, сохранение корреляции после неизвестного
результата и наблюдаемые ограничения повтора. Не приписывать CLI скрытый retry,
если его нет в контракте.

Зафиксировать, какие изменения иерархии, опций, значений, полей, порядка,
форматов, сообщений и статусов нарушают совместимость.
