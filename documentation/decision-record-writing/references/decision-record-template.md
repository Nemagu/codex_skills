# Каркас записи решения

Адаптировать каркас к содержанию: не заполнять разделы механически и не создавать
альтернативы ради формы. Простой связный текст допустим вместо таблицы. Удалить
пояснения и заполнители из результата. Сохранить сведения об ID, дате, статусе
и заключительный раздел открытых вопросов. Дату указывать в формате YYYY-MM-DD;
для прежнего решения не выдумывать неизвестную дату его принятия.

```markdown
# <DR-ОБЛАСТЬ-НОМЕР>. <Название решения>

Дата: <дата записи>
Статус: <статус>

## Контекст

Проблема, причины рассмотрения изменения и значимые ограничения.
Прежнее поведение — в объёме, необходимом для понимания выбора.

## Область изменения

|Слой|Элемент|Изменение|
|:---|:---|:---|
|<слой>|<контекст, название / стабильное обозначение>|<как было и как станет>|

## Решение

Выбранный подход и новое поведение. В черновике явно обозначить предложение.

## Обоснование

Причины выбора, критерии и принятые компромиссы.

## Альтернативы

Реально рассмотренные варианты и причины отказа либо оставшиеся различия
между обсуждаемыми вариантами. Если альтернативы неизвестны, не придумывать их.

## Последствия

Преимущества, издержки, риски и необходимые связанные изменения.
Если обновление спецификаций предстоит, явно указать это и затронутые контракты.

## Открытые вопросы

<Нерешённые вопросы либо «Открытых вопросов нет.»>
```

При пересмотре добавить в подходящем месте ID и название связанного решения,
а при частичной замене — изменяемую и сохраняющуюся части. При отмене — причину
и последствия. Файловые ссылки и координаты Git для понимания записи не нужны.
