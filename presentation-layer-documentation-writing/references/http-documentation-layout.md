## Глобальные решения

До создания файлов согласовать:

- области доступности API, например публичную и приватную;
- способ и расположение версии контракта;
- базовый адрес и порядок его сегментов;
- состав ресурсов и операций;
- общие контракты идентичности, пагинации и ошибок;
- политику результатов команд;
- порог разбиения моделей по файлам;
- структуру навигации.

Не создавать пустой раздел области доступности или версии до появления первого
контракта. Не переносить подтверждённое устройство одного сервиса в другой без
согласования.

## Дерево файлов

Отражать область доступности и версию в структуре документации:

```text
http/
├── README.md
├── public/
│   ├── README.md
│   └── v1/
│       ├── README.md
│       ├── common/
│       │   ├── README.md
│       │   ├── identity.md
│       │   ├── pagination.md
│       │   └── errors.md
│       └── resources/
│           └── <resource>/
│               ├── README.md
│               ├── enums.md
│               ├── endpoints/
│               └── models/
└── private/
    └── <version>/
```

Конкретные имена областей, версии и сегментов адреса брать из согласованного
контракта. Например, структура `public/v1` может соответствовать адресу
`/<service>/api/public/v1/<resource>`, но этот порядок не считать универсальным.

Размещать общий документ выше только при одинаковой семантике у всех его
потребителей. Правила конкретной области и версии хранить внутри неё, а не в
корне HTTP-документации.

## Навигация

`SUMMARY.md` должен повторять смысловую иерархию файлов:

```text
HTTP API
└── Публичное API
    └── Версия 1
        ├── Общие контракты
        └── Ресурсы
```

Добавлять в навигацию документы области, версии, ресурса, моделей и каждой точки
входа. Не оставлять ненавигационные дубликаты старой структуры.

Пользовательские названия в `SUMMARY.md`, заголовках и ссылках писать на языке
документации. Не использовать имена классов реализации как названия моделей.

## Документ ресурса

В `resources/<resource>/README.md` фиксировать:

- назначение и границы ресурса;
- базовый адрес;
- требования идентичности;
- таблицу операций со ссылками на отдельные endpoint-документы;
- ссылки на запросы, ответы и перечисления;
- применимые общие контракты;
- готовность и открытые вопросы.

Не объединять спецификации разных ресурсов в один файл ради сходства операций.

## Точки входа

Каждую HTTP-точку входа хранить в отдельном файле `endpoints/<operation>.md`.
Фиксировать метод, полный адрес, идентичность, входное содержимое, успешный
статус, модели, преобразование в application-контракт, повтор и отклонения от
общих исходов.

Не повторять в endpoint-документе общий каталог ошибок. Если endpoint полностью
следует общему контракту, не создавать в нём раздел ошибок: ссылка ресурса на
`common/errors.md` достаточна. Создавать раздел endpoint-а только для отклонения
и описывать в нём:

- дополнительный статус;
- неприменимый общий статус, если это неочевидно;
- отличающиеся сведения ответа;
- особое правило повтора.

## Модели

Presentation-модели принадлежат HTTP-контракту и не являются application DTO.
Для каждого поля модели использовать отдельную строку таблицы. Не объединять
несколько полей в одной строке даже при одинаковом представлении.

Разделять модели запросов и ответов. По умолчанию применять согласуемый порог:

- до трёх моделей одного направления можно хранить в `requests.md` или
  `responses.md`;
- при четырёх и более моделях создавать одноимённый каталог, индексный
  `README.md` и отдельный файл каждой модели.

Не вводить языковые имена моделей. Использовать предметные названия на языке
документации: «Создание сотрудника», «Версия сотрудника», «Страница сотрудников».

## Перечисления

Размещать перечисление рядом с ресурсом, который его использует. Для сотрудника
это могут быть `/employees/roles`, `/employees/statuses` и `/employees/events`.
Не создавать глобальный HTTP-ресурс перечислений, если значения принадлежат
конкретному ресурсу.

Для каждого адреса перечисления создавать отдельный endpoint-документ и связывать
его с отдельным application-запросом и DTO результата. В `enums.md` ресурса
показывать адрес и допустимые значения. Общую presentation-модель элемента
переиспользовать только при одинаковой семантике значения и подписи.

## Результаты команд

На глобальном этапе предложить и согласовать политику минимальных ответов:

- `GET` возвращает запрошенные данные;
- создание возвращает только идентификатор созданного агрегата, необходимый для
  последующего `GET`;
- изменение, удаление и восстановление возвращают `204 No Content` без тела,
  поскольку идентификатор уже известен клиенту;
- актуальное состояние клиент получает отдельным `GET`-запросом.

Не возвращать снимок агрегата из команды только потому, что application-операция
его предоставляет. Явно описывать, какие сведения application-результата
раскрываются или отбрасываются. Если пользователь выбрал другую политику,
документировать её последовательно для всех ресурсов.

## Общие ошибки

Типовой формат ошибки и общий набор статусов хранить один раз в
`common/errors.md`. Отделять транспортную валидацию, публичные application-исходы
и неизвестный внутренний сбой. Каждый использующий его ресурс должен ссылаться на
этот документ в своём README. Не раскрывать внутренние исключения.

Упорядочивать статусы так, чтобы временная недоступность `503`, если она
предусмотрена, находилась после общего внутреннего сбоя `500`.

## Примеры JSON

Форматировать JSON для чтения на узком экране:

- открывающую и закрывающую скобки ставить на отдельных строках;
- каждое поле объекта помещать на отдельную строку;
- вложенные объекты форматировать с отступом;
- не использовать однострочные объекты;
- примеры не должны добавлять полей или гарантий сверх нормативных таблиц.

## Адаптация существующей документации

Использовать существующую согласованную документацию как источник исходных
данных и ссылок. Код репозитория не читать без отдельного разрешения пользователя.
Запрашивать такое разрешение только при адаптации существующей документации,
когда без реализации нельзя разрешить конкретное расхождение.

Перед перемещением файлов найти все входящие ссылки. После переноса удалить или
сохранить вне рабочей структуры устаревшие дубликаты, обновить `SUMMARY.md` и
проверить локальные Markdown-ссылки и сборку документации.
