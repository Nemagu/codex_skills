# Структура документации HTTP API

## Иерархия

Разделять область доступности, версию и ресурсы:

```text
presentation/http/
├── README.md
├── public/
│   └── v1/
│       ├── README.md
│       ├── common/
│       └── resources/
└── private/
    └── v1/
```

Названия каталогов являются примером структуры, а не обязательными сегментами
URL. Адрес согласовывать отдельно.

Для ресурса использовать:

```text
resources/<resource>/
├── README.md
├── enums.md
├── endpoints/
├── models/
│   ├── requests.md
│   └── responses.md
```

Каждый endpoint хранить в отдельном файле. До трёх моделей одного направления
допустимо хранить в общем файле; при четырёх и более создавать каталог,
`README.md` и отдельный файл каждой модели.

Перечисления размещать рядом с использующим ресурсом. Для получаемого клиентом
перечисления создавать отдельный endpoint и application-запрос. Не создавать
глобальный каталог перечислений без общей предметной принадлежности.

## Документ ресурса

Фиксировать назначение, границы, базовый адрес, идентичность, таблицу операций,
ссылки на модели и перечисления, применимые общие контракты, готовность и вопросы.

## Общие документы

Выносить ошибку, пагинацию, идентичность или заголовок только при общей семантике
у нескольких ресурсов. Документ ресурса должен ссылаться на применимые общие
контракты. Endpoint описывает только явное отклонение.

## Навигация

Фрагмент `SUMMARY.md` внутри раздела presentation должен повторять иерархию и
включать:

- документы HTTP, области и версии;
- все общие контракты;
- каждый ресурс;
- каждый endpoint, включая перечисления;
- каждую модель и индексный файл каталога моделей.

Пользовательские названия писать на языке документации. После перемещения файлов
удалять ненавигационные дубликаты и проверять все локальные ссылки.

Фрагмент начинается с `presentation/http/README.md` и не содержит соседние
presentation-разделы либо корневые разделы документации.

## Стабильные обозначения

Использовать иерархию `<контекст>.presentation.http.<область>.<версия>.<ресурс>.<уточнения...>`.
Количество уточняющих сегментов не ограничивать. Обозначение должно различать
публичный и приватный контракт, версии, endpoint и модели; не использовать имена
классов реализации.
