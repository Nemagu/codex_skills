# Контракт HTTP endpoint-а

## Метод и адрес

Для endpoint-а фиксировать отдельными строками метод, полный шаблон адреса,
область, версию, идентичность, входной и выходной content type, application-
операцию и стабильное обозначение. Явно определять каноничность завершающего `/`.
Все эти сведения, успешный статус, заголовки и модель ответа помещать в единую
таблицу паспорта. Не добавлять после паспорта смешанный прозаический блок с
повтором адреса, query-параметров и успешного ответа.

## Вход

Раздельно описывать path, query, headers, cookies и body. Для каждого значения
использовать отдельную строку:

|Поле|Источник|Представление|Обязательность|Правила|
|:---|:---|:---|:---|:---|

В столбце `Поле` использовать русское предметное название; внешнее английское
имя указывать в `Источник`. Не объединять поля. Фиксировать отсутствие, `null`, пустое значение, default,
нормализацию, неизвестные поля и автоматическую конверсию. Для коллекционного
query-параметра определять повторяемость, разделитель, порядок, дубликаты и пустой
элемент.

Для списков отдельно определять:

- все фильтры и их совместное действие;
- сортировку, направление и разрешение равенства;
- пагинацию и границы;
- стабильность порядка между запросами;
- поведение при отсутствии результатов.

Параметры пагинации по умолчанию необязательны для клиента и имеют явно
зафиксированные значения по умолчанию. Минимальный пример не передаёт их без
необходимости. Успешный пример страницы содержит один реальный объект `results`;
пустую выборку показывать только как отдельный граничный пример.

## Модели

Запросы и ответы описывать отдельно. Для каждого поля — одна строка с предметным
русским названием, внешним именем, представлением, обязательностью, допустимостью
`null`, ограничениями и смыслом. Не использовать названия классов или языковые
типы как нормативные названия моделей.

Общая модель ошибки должна содержать стабильный машинный код, безопасное
сообщение для человека и структурированные детали, а также отдельную строку каждого поля,
структуру вложенных данных, обязательность, `null` и пример. Ошибку транспортной
валидации не копировать из модели конкретного фреймворка.

## Преобразования

Показывать входную трассировку:

|Внешнее значение|Источник|Поле application-входа|Преобразование|
|:---|:---|:---|:---|

Включать path, query, body, идентичность и контекст. Явно отмечать отброшенные
внешние сведения и application-поля, которые presentation не заполняет.

Для результата использовать:

|Поле application-результата|Внешнее поле|Преобразование|Раскрытие|
|:---|:---|:---|:---|

При ответе без тела явно фиксировать отсутствие выходной модели.

## Результаты и ошибки

Для успешного ответа фиксировать статус, заголовки, тело и модель. Для создания
отдельно согласовывать `200` или `201`, наличие `Location` и его формат.

Общие ошибки хранить один раз. Они должны различать транспортную валидацию,
публичные application-исходы и неизвестный сбой. Не называть domain-ошибку
непосредственным источником HTTP-ответа. В endpoint-е перечислять ошибки только
при отклонении от общего контракта. `503`, если предусмотрен, располагать после
`500`.

## Повтор и совместимость

Определять безопасность повтора, ключ идемпотентности и наблюдаемый результат
дубликата, если применимо. Фиксировать гарантированные поля, нарушающие
совместимость изменения и правила поддержки версий.

## Примеры

Добавлять минимальный успешный пример входа и ответа. Для endpoint-а без тела
показывать вход и явно писать, что тело ответа отсутствует. Для сложной
валидации добавлять пример ошибки.

JSON форматировать многострочно: каждая скобка и каждое поле — на отдельной
строке, вложенность — с отступом. Каждое показанное поле должно быть описано в
нормативной таблице; пример не вводит гарантий.
