# Структура документации

## Владение структурой

Главный скил определяет архитектурные слоты верхнего уровня. Специализированные
скилы развивают только внутреннее поддерево назначенного слота. Не создавать
отдельный корень по названию транспорта, технологии или скила, если для него уже
существует слот владельца.

Сначала учитывать обязательные инструкции и механизм сборки целевого репозитория.
Если структура ещё не согласована, использовать следующий канон:

```text
docs/
├── README.md
├── SUMMARY.md
├── context.md
├── domain/
│   ├── README.md
│   ├── aggregates/
│   ├── projections/
│   ├── value-objects/
│   ├── services/
│   └── events/
├── application/
│   ├── README.md
│   ├── contracts/
│   ├── operations/
│   │   ├── commands/
│   │   └── queries/
│   └── scenarios/
├── presentation/
│   ├── README.md
│   ├── http/
│   ├── messages/
│   └── background-processes/
├── external-contracts/
│   ├── README.md
│   └── outgoing/
├── adapters/
│   ├── README.md
│   ├── incoming/
│   └── outgoing/
└── observability/
    ├── README.md
    └── logging/
        └── README.md
```

Создавать только разделы, для которых существуют документы. Не создавать пустые
каталоги и индексные страницы «на будущее».

## Архитектурные слоты

|Слот|Содержимое|Не содержит|
|:---|:---|:---|
|`domain`|Агрегаты, сущности, проекции, объекты-значения, сервисы и доменные события|Application-операции и внешние модели|
|`application`|Команды, запросы, DTO, порты и составные сценарии|Транспортные модели и реализации портов|
|`presentation/http`|Входящие HTTP-контракты и преобразования|Application DTO как внешние модели|
|`presentation/messages`|Входящие сообщения и их обработка на границе|Исходящие сообщения и runtime consumer-а|
|`presentation/background-processes`|Внутренние инициаторы application-операций, расписание и lifecycle|Реализация runtime и application-логика|
|`external-contracts/outgoing`|Контракты, публикуемые сервисом внешним потребителям|Реализация publisher-а|
|`adapters/incoming`|Паспорта неочевидных реализаций входящих границ|Нормативные presentation-контракты|
|`adapters/outgoing`|Паспорта реализаций application-портов|Владение application-портами и внешними контрактами|
|`observability`|Сквозные эксплуатационные контракты сервиса: логирование и другие согласованные сигналы наблюдаемости|Реализацию logging-адаптеров и контракты отдельных архитектурных слоёв|

Внутри `observability` создавать отдельное индексное поддерево для каждого
согласованного сигнала. Для логирования по умолчанию использовать
`observability/logging/README.md`; общий контракт и профили процессов добавлять
дочерними документами без дублирования. Не создавать страницы метрик,
трассировки и других будущих сигналов до появления требований.

Документ размещать по владельцу контракта, а не по технологии реализации. Один
файл имеет один канонический путь. Связи с другими слоями выражать ссылками, а не
копиями документа.

## Внутренняя группировка

Внутри слота группировать сначала по устойчивой смысловой категории или
бизнес-возможности. Транспорт, инициатор и технология использовать только там,
где они являются частью ответственности данного слота.

Для небольшого набора документов допускать плоскую структуру. Создавать индексный
каталог, если выполняется хотя бы одно условие:

- на уровне более 12 документов;
- есть минимум две устойчивые группы по два документа;
- имена требуют повторяющихся префиксов;
- для поиска уже нужен отдельный индекс;
- согласованный рост заведомо приведёт к одному из этих условий.

Не упрощать принятую структуру автоматически: стабильность ссылок важнее удаления
одного уровня.

## Имена и ссылки

- Следовать соглашению репозитория; при его отсутствии использовать английский
  `kebab-case` для технических имён файлов и каталогов.
- Служебные файлы называть `README.md` и `SUMMARY.md`.
- Отображаемые заголовки и подписи ссылок писать на языке документации.
- Делать относительные ссылки и проверять их после каждого перемещения.
- Каждый содержательный файл включать в локальный индекс и глобальный
  `SUMMARY.md` согласно их ответственности.

## Изменение структуры

Перемещение завершено только когда:

1. создан новый канонический путь;
2. обновлены локальные README;
3. обновлён `SUMMARY.md`;
4. исправлены все входящие относительные ссылки;
5. удалён старый навигационный путь;
6. сборка документации и проверка ссылок успешны.

Массовое перемещение существующей документации выполнять только после
согласования целевого дерева.
