## Базовая структура

Сначала учитывать инструкции, генератор документации и соглашения целевого
репозитория. Структуру ниже использовать только как возможную отправную точку,
когда подходящего соглашения ещё нет и сервис разделён на бизнес-контексты с CQRS
в application-слое:

```text
docs/
├── contexts/
│   ├── README.md
│   └── <context>/
│       ├── README.md
│       ├── aggregates/
│       ├── projections/
│       ├── value-objects/
│       ├── services/
│       └── events/
│           └── domain/
├── pipelines/
│   ├── README.md
│   ├── operations/
│   │   ├── commands/
│   │   │   └── <business-capability>/
│   │   │       ├── user/
│   │   │       └── system/
│   │   └── queries/
│   │       └── <business-capability>/
│   │           ├── user/
│   │           └── system/
│   └── scenarios/
│       └── <business-capability>/
│           ├── user/
│           └── system/
├── external-contracts/
│   └── <adapter-or-contract-category>/
└── adapters/
    ├── README.md
    ├── incoming/
    └── outgoing/
```

Создавать только нужные каталоги. Доменные события хранить внутри владеющего
контекста. Интеграционные и транспортные контракты размещать в разделе внешнего
слоя по соглашениям репозитория; не считать каталог из примера обязательным.

Структуру документов внешних контрактов добавлять только после их проектирования
соответствующим специализированным навыком либо отдельной согласованной
спецификацией. Координатор определяет место раздела в общей навигации, но не
выбирает транспорт и внутреннее устройство этого раздела.

Паспорта адаптеров размещать канонически:

```text
docs/adapters/incoming/<adapter-name>.md
docs/adapters/outgoing/<adapter-name>.md
```

Имя файла и вложенных каталогов писать в `kebab-case` независимо от языка
реализации. `incoming` использовать для входящих адаптеров, `outgoing` — для
реализаций исходящих портов. Не создавать `docs/adapters/` и его подкаталоги, пока
не появился хотя бы один неочевидный адаптер. `README.md` создавать вместе с первым
паспортом; он кратко объясняет назначение раздела и содержит ссылки на все паспорта.

## Развитие структуры прикладного слоя

Для небольшого количества документов допускать плоское размещение внутри
`commands`, `queries` и `scenarios`. Переходить к каталогам бизнес-возможностей,
если выполняется хотя бы одно условие:

- на одном уровне накопилось более 12 документов;
- определены минимум две устойчивые бизнес-возможности, каждая из которых
  объединяет не менее двух документов;
- имена файлов требуют повторяющихся префиксов для различения групп;
- для поиска операции уже нужен отдельный индекс;
- согласованный ближайший рост заведомо приведёт к одному из этих условий.

Бизнес-возможность использовать как основной признак группировки. Она выражает
устойчивую бизнес-цель или функциональную область и не обязана совпадать с
агрегатом либо bounded context. Использовать одинаковые названия возможностей в
`commands`, `queries` и `scenarios`.

Внутри возможности создавать каталоги `user` и `system` только при наличии обоих
видов операций или когда это заметно улучшает навигацию. Для большого количества
системных операций допустимо добавить группировку по источнику.

Не использовать в качестве основных групп транспорт, вид воркера, `crud`,
`handlers`, `services` или `common`. Составной сценарий размещать по его конечной
пользовательской или системной цели, а не по первой операции или агрегату.

Уровень bounded context перед бизнес-возможностью считать необязательным:

```text
commands/<bounded-context>/<business-capability>/
```

Добавлять его только когда в сервисе несколько явно определённых bounded context,
большинство операций однозначно принадлежит одному из них и минимум в двух
контекстах уже существует несколько бизнес-возможностей. Межконтекстную операцию
или сценарий не помещать в один контекст искусственно; группировать по общей
бизнес-цели.

Не создавать каталог для единственного документа без ожидаемого роста. После
усложнения структуры не упрощать её автоматически только из-за уменьшения числа
файлов: стабильность ссылок и навигации важнее минимального числа каталогов.

## Имена файлов и каталогов

Следовать существующему соглашению репозитория. Для паспортов адаптеров использовать
каноническое размещение и `kebab-case`, чтобы их структура совпадала между сервисами. Не
смешивать разные стили в одном разделе и не переименовывать существующие файлы массово без
отдельного согласования.

Если соглашения нет, предложить один понятный формат и согласовать его до создания
файлов. `snake_case`, `kebab-case` и другие варианты считать допустимыми; выбор не
должен зависеть от языка реализации. Сохранять служебные имена, требуемые
генератором или навигацией, например `README.md` и `SUMMARY.md`.

Локальные объекты-значения и доменные сервисы описывать в документе агрегата.
Выносить их в отдельные каталоги, когда они используются несколькими объектами
контекста.

Если application-слой использует CQRS и структура из примера согласована,
канонические команды и запросы хранить в разделе операций, а составные сценарии —
в разделе сценариев со ссылками на операции. Не создавать `pipelines`,
`commands`, `queries` или каталоги бизнес-возможностей только потому, что они
присутствуют в примере.

Не создавать разные документы только из-за HTTP, брокера, командной строки или
другого адаптера при одинаковом application-контракте.

После создания файла обновлять существующий индекс или навигацию, например
`SUMMARY.md`, только если такой механизм уже используется. Ссылки делать
относительными и двусторонними там, где они помогают перейти от агрегата к событию
или от пайплайна к операции.

Не размещать большое количество однотипных файлов плоским списком в навигации.
При росте раздела создавать индексные страницы и группировать документы прежде
всего по принятой бизнес-возможности. Инициатора и системный источник использовать
как вторичные признаки. Каждый содержательный Markdown-файл должен оставаться
достижимым из основной навигации.

Перед завершением проверять, что:

- каждый новый файл включён в используемый индекс или `SUMMARY.md`;
- относительные Markdown-ссылки разрешаются в существующие файлы;
- служебные `README.md` описывают назначение группы, а не дублируют дочерние
  спецификации;
- одинаковые типы документов используют одинаковый порядок основных разделов;
- паспорта адаптеров размещены в `docs/adapters/incoming|outgoing/`, названы в
  `kebab-case` и доступны из `docs/adapters/README.md`;
- структура каталогов не выдаёт архитектурный вариант из примера за обязательный;
- внешние контракты не размещены среди доменных событий.
