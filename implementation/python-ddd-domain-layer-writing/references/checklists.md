# Чек-листы

## Перед реализацией

Извлеки из задачи и зафиксируй без дополнений:

- [ ] заданные агрегаты, сущности и проекции;
- [ ] точный состав полей и бизнес-типы;
- [ ] создание, восстановление и начальную версию;
- [ ] состояния и переходы, если они заданы;
- [ ] инварианты, операции, отказы и семантику повторов;
- [ ] требуемые доменные сервисы и интерфейсы чтения;
- [ ] явно заданные связи идентификаторов.

Не добавляй типовые поля, состояния, операции, ID-parity или сервисы. Если часть
контракта неоднозначна, реализуй независимые определённые части и не придумывай
недостающую бизнес-семантику.

---

## Чек-лист добавления агрегата

### Шаг 1 — Создать поддиректорию

`domain/<aggregate_name>/` (snake_case, единственное число).

### Шаг 2 — `value_object.py`

Создать в порядке зависимости:

- [ ] Отдельный неизменяемый VO для каждого заданного поля.
- [ ] VO создаются в порядке зависимостей.
- [ ] Реализованы только заданные нормализация, ограничения и равенство.

### Шаг 3 — `aggregate.py`

- [ ] Импорты: `AggregateRootWithState` или `AggregateRoot` из `domain.aggregate`, нужные ошибки, ID-VO связанных агрегатов из их витрин, локальные VO из `value_object.py`, общие VO из `domain.value_object`.
- [ ] Класс `<Aggregate>(AggregateRootWithState)` или `<Aggregate>(AggregateRoot)`.
- [ ] `_DELETED_MSG: ClassVar[str] = ...` (плюс другие `_*_MSG` при расширенном состоянии).
- [ ] Конструктор: параметры — VO; вызов `super().__init__(...)` с `domain_object_name=DomainObjectName("...")`; присваивание приватных полей.
- [ ] Properties для всех приватных полей (read-only, имя без `_`).
- [ ] Коллекции VO хранятся и возвращаются как `frozenset` или `tuple`.
- [ ] Перед мутацией выполнены все заданные проверки.
- [ ] Успешная изменяющая операция увеличивает версию ровно один раз.
- [ ] При отказе поля и версия остаются неизменными.
- [ ] Реализация `_error_data`.
- [ ] Если есть кросс-агрегатные инварианты — публичные `validate_*` методы.
- [ ] Если участвует в политиках — `raise_*` методы (бросают `EntityPolicyError`).

### Шаг 4 — `factory.py`

- [ ] Класс `<Aggregate>Factory`, все методы `@staticmethod`.
- [ ] `new(...)`: принимает переданный вызывающим слоем ID и остальные данные
      только как VO; задаёт только явно установленные начальные значения.
- [ ] `restore(...)`: принимает все поля только как VO, включая `state` и `version`; возвращает агрегат в любом валидном состоянии.
- [ ] Raw-данные преобразуются в VO до вызова фабрики; методов `from_raw` нет.
- [ ] Прямой вызов конструктора агрегата вне фабрики отсутствует.

### Шаг 5 — `repository.py` (опционально)

Создаётся только для заданного доменного сервиса, которому необходим
специализированный поиск.

- [ ] Класс `<Aggregate>ReadRepository(ABC)`.
- [ ] Все методы — `async`, `@abstractmethod`, тело `...`, имя `by_<criteria>`.
- [ ] Параметры — VO, возврат — `<Aggregate> | None` или `list[<Aggregate>]`.

### Шаг 6 — `service.py` (опционально)

- [ ] Каждый сервис проверяет одно конкретное бизнес-правило и не создаёт агрегат.
- [ ] Имя сервиса отражает правило, а не техническую категорию.
- [ ] Repository-интерфейс добавлен только если он требуется этой проверке.
- [ ] Если объекты можно загрузить заранее, сервис принимает готовые агрегаты и VO.
- [ ] Сервис не оркестрирует загрузку нескольких объектов и генерацию ID.

### Шаг 7 — `__init__.py`

- [ ] Импорт всех публичных классов агрегата.
- [ ] `__all__` со всеми именами в алфавитном порядке.
- [ ] Импорты внутри файла отсортированы по полному пути.

## Чек-лист добавления проекции

Отличается от агрегата в нескольких местах. Шаги, где нет различий, — кратко.

### Шаг 1 — Поддиректория

`domain/<projection_name>/`.

### Шаг 2 — `value_object.py`

- [ ] Отдельный неизменяемый VO для каждого заданного поля проекции.
- [ ] ID-parity реализован только при наличии явного требования.

### Шаг 3 — `projection.py` (не `aggregate.py`!)

- [ ] Импорты: `ProjectionWithState` или `Projection` из `domain.projection`.
- [ ] Класс `<Projection>(ProjectionWithState)` или `<Projection>(Projection)`.
- [ ] **Никаких** `_DELETED_MSG` — у проекции нет `_check_state`.
- [ ] Конструктор с `super().__init__(..., domain_object_name=DomainObjectName("..."))`.
- [ ] Properties для всех приватных полей.
- [ ] Реализованы только заданные операции проекции.
- [ ] Новая версия принимается извне и не инкрементируется проекцией.
- [ ] Transport-модели и application DTO не передаются в domain.
- [ ] Реализация `_error_data` с `subject=self._domain_object_name.name`.

### Шаг 4 — `factory.py`

- [ ] Обязательные `new(...)` и `restore(...)` принимают все данные только как VO.
- [ ] Идентификатор передаётся вызывающим слоем; фабрика его не генерирует.
- [ ] Прямой вызов конструктора проекции вне фабрики отсутствует.

### Шаг 5 — `repository.py` (опционально)

- [ ] Read-интерфейс существует только для заданного доменного правила.

### Шаг 6 — `service.py` (опционально)

- [ ] Сервис не создаёт проекцию, а проверяет отдельное бизнес-правило.

### Шаг 7 — `__init__.py`

- [ ] Импорты всех публичных классов проекции.
- [ ] `__all__` алфавитно.

## Что делать после domain-слоя

Этот скил отвечает только за domain. После добавления агрегата/проекции для полной интеграции потребуется:

- **`application/ports/repositories/<aggregate>.py`** — полный repository-интерфейс с read + save + version.
- **`application/commands/...` и/или `application/queries/...`** — use case'ы, использующие новый агрегат.
- **`infrastructure/db/...`** — реализация репозиториев, миграции.
- **`presentation/api/...`** — роутер и Pydantic-модели, если агрегат экспонируется по API.

Эти шаги — за пределами domain-скила.

## Финальная проверка

Перед тем как считать domain-часть готовой:

- [ ] Все импорты внутри `domain/` идут только из `domain/` или стандартной библиотеки.
- [ ] Витрина (`__init__.py`) обновлена, `__all__` синхронизирован с реальными именами.
- [ ] Каждое мутирующее поведение реализует только заданные проверки состояния и
      семантику повторного вызова.
- [ ] Каждое успешное поведение, меняющее агрегат, увеличивает версию ровно один раз.
- [ ] После доменного отказа состояние и версия не изменены.
- [ ] У проекции **нет** `_update_version` в state-методах и нет `_check_state`.
- [ ] `data` ошибок собирается по конвенции (английский snake_case ключ-сущность на верхнем уровне, поля сущности внутри).
- [ ] Все приватные поля начинаются с `_` и имеют read-only `@property`.
- [ ] Каждое поле представлено отдельным неизменяемым VO.
- [ ] Агрегаты и проекции создаются и восстанавливаются только через фабрики.
- [ ] В domain нет event sourcing, outbox и коллекции событий агрегата.
