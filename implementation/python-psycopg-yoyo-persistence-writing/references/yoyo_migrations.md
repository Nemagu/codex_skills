1. Перечислить таблицы и назначение изменения.
2. Показать схему каждой создаваемой или изменяемой таблицы.
3. Показать старое и новое состояние столбцов, перенос данных и риск.
4. Перечислить ключи, связи, ограничения и разрешённые индексы.
5. Показать apply, rollback, совместимость и риск блокировок.
6. Получить явное подтверждение до изменения файлов.

## Файлы и зависимости

- Следовать существующей конвенции имён.
- Использовать `step` и явный `__depends__`.
- Не полагаться только на порядок файлов.
- Держать одно логически цельное изменение в миграции.
- Реализовывать apply и rollback.
- Перед перезаписью перечислить точные файлы и получить разрешение.
- При запрете перезаписи создать корректирующую миграцию.
- Не импортировать runtime domain/application-код.
- Фиксировать необходимые enum/форматы внутри migration-only кода.

Yoyo выполняет миграцию в отдельной транзакции, а шаги изолирует savepoints.
Нетранзакционный DDL помещать в отдельную миграцию с
`__transactional__ = False`; не смешивать его с операциями общей атомарности.

## Индексы и ограничения

Любой индекс требует явного разрешения. Показать таблицу, колонки, метод,
условие, ускоряемые запросы, цену записи, размер и блокировки.

Уникальный индекс и `UNIQUE` согласовывать отдельно: назвать бизнес-правило и
стратегию для существующих дубликатов. Это относится и к `UNIQUE`, неявно
создающему индекс.

Перед `NOT NULL`, `CHECK`, `UNIQUE` и foreign key проверять существующие данные.
Не исправлять конфликты молча и не добавлять фиктивный default ради прохождения.
Временный default удалить после backfill, если он не часть постоянного контракта.

## Безопасное изменение работающей схемы

Для несовместимых изменений применять expand → migrate → contract:

1. Добавить совместимую структуру.
2. Перенести и проверить данные.
3. Перевести код.
4. Удалить старую структуру отдельным подтверждённым шагом.

- Учитывать размер таблиц и блокировки.
- Длительный backfill выполнять контролируемыми порциями.
- Не отключать целостность ради скорости.
- `lock_timeout`/`statement_timeout` задавать локально и после согласования.
- Не использовать `IF EXISTS`/`IF NOT EXISTS` для сокрытия неожиданной схемы.
- Разрушительные операции подтверждать отдельно с оценкой потерь и отката.
- Не обещать rollback данных, если исходные значения потеряны.

## Дополнительные объекты и права

Для enum, sequence, view, materialized view, function, trigger, extension и
schema показывать определение, назначение, зависимости, влияние, права и rollback.

Не менять owner, roles, grants и default privileges без требования. Перед
изменением показать роли и права. Не создавать пароли и не требовать superuser
как постоянный runtime-режим.

## Конфигурация и запуск

- Использовать backend `postgresql+psycopg` для psycopg 3.
- Получать DSN из настроек/окружения, не раскрывать пароль в командах и выводе.
- Автоматически применять миграции только к временной тестовой БД.
- Общие development/staging/production БД изменять только по отдельной просьбе.
- Использовать штатную блокировку yoyo при программном применении.

## Проверка

1. Поднять чистую временную PostgreSQL-БД.
2. Применить всю цепочку через yoyo.
3. Проверить фактическую схему.
4. Откатить новую миграцию через yoyo.
5. Применить её повторно.
6. Запустить integration-тесты адаптера.
7. Проверить pending/divergent состояние.
8. Удалить временную инфраструктуру.

Для data migration проверять пустые, валидные и конфликтные данные. Не исполнять
SQL из файла вручную в обход yoyo. Для согласованной необратимой миграции явно
фиксировать невозможность rollback-проверки.
