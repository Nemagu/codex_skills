# Глобальные инструкции Codex

## Сохранение рабочего контекста

- Для задач, включающих содержательное планирование, опрос пользователя, сбор требований, несколько этапов работы или вероятное продолжение в другой сессии, сохранять актуальное рабочее состояние вне проектных репозиториев в `~/.codex/task_state/`.
- Для проектной задачи использовать путь `~/.codex/task_state/<project-key>/<task-key>.md`. `project-key` определять автоматически как имя корня проекта и короткий хеш его канонического абсолютного пути; корнем считать Git root, а при его отсутствии — текущий рабочий каталог. `task-key` формировать из краткого стабильного названия задачи. Для задачи вне проекта использовать `~/.codex/task_state/_global/<task-key>.md`.
- Не просить пользователя выбирать или повторно указывать путь. В начале использования рабочего файла кратко сообщить его фактический путь.
- Создавать или обновлять рабочий файл после появления содержательного плана, подтверждённых требований либо ответов пользователя, существенных для дальнейшей работы. После каждого ответа, меняющего требования, решения или план, обновлять файл до продолжения реализации.
- Хранить в рабочем файле цель, подтверждённые требования и ответы пользователя, принятые решения, допущения, открытые вопросы, план, текущее состояние и результаты проверок. Поддерживать актуальное состояние вместо полной стенограммы; устаревшие решения удалять либо явно отмечать отменёнными.
- При возобновлении или продолжении многоэтапной задачи сначала найти и прочитать соответствующий рабочий файл, сверить его с текущим запросом и только затем продолжать работу. Не смешивать состояние разных задач.
- Не сохранять в рабочих файлах секреты, токены, пароли и другие чувствительные данные. Не удалять рабочие файлы автоматически после завершения задачи.
- `/tmp` использовать только для воспроизводимых промежуточных данных, которые не нужны для восстановления контекста. Не хранить там единственную копию планов, требований, решений или ответов пользователя.

## Правила создания Git-коммитов

- Явная просьба пользователя «сделай коммит», «закоммить» или аналогичная считается разрешением выполнить необходимые `git add` и `git commit`. Дополнительное согласование плана и сообщения коммита не требуется.
- Перед коммитом проверить `git status`, staged/unstaged diff и убедиться, что в коммит не попадут секреты, временные файлы, артефакты окружения или посторонние изменения.
- Не изменять, не удалять и не откатывать пользовательские изменения, не относящиеся к задаче.
- Если изменения относятся к разным задачам, разделить их на логически самостоятельные коммиты. Если границы неоднозначны или часть изменений выглядит посторонней, запросить уточнение.
- Если пользователь согласовал разделение изменений на несколько коммитов, создать все согласованные коммиты без промежуточного подтверждения каждого из них.
- Добавлять в индекс только явно относящиеся к выбранному коммиту файлы или части файлов. Не использовать `git add .` и `git add -A`, если в рабочем дереве есть несвязанные изменения.
- Соблюдать формат сообщений, установленный репозиторием. Если формат не установлен, использовать Conventional Commits: `<type>(<scope>): <summary>`.
- Допустимые типы по умолчанию: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`.
- Заголовок и описание коммита должны быть написаны на английском языке.
- Summary писать кратко, в повелительном наклонении и без точки в конце.
- Рекомендуемая длина заголовка — не более 100 символов; при необходимости допускается до 150 символов. Это мягкое ограничение: ясность и точность важнее формального лимита.
- Каждый коммит должен содержать описание (commit body), отделённое от заголовка пустой строкой.
- В описании кратко указать, что изменено и почему. Жёсткого ограничения длины описания нет.
- Перед коммитом запускать проверки, предписанные инструкциями репозитория. Если специальных инструкций нет, запускать релевантные форматирование, линтер и тесты в объёме, пропорциональном изменениям.
- Если обязательная проверка завершилась ошибкой, не создавать коммит без отдельного разрешения пользователя; сообщить причину и существенный фрагмент ошибки.
- Если проверки невозможно запустить из-за отсутствующей инфраструктуры или окружения, сообщить об этом и запросить решение только тогда, когда без него коммит запрещён правилами репозитория.
- Не использовать `--no-verify`, не изменять существующие коммиты через `--amend`, не выполнять rebase, force push или push без явной просьбы пользователя.
- После создания коммита проверить итоговый `git status` и сообщить хеш, сообщение, включённые изменения и результаты проверок.
